1.2 现实是什么（问题的实际表现）

🧠

认知负担爆表

改一个小功能要通读几千行；加一个 TTS 供应商，要在 309 行引擎文件里精准定位 synthesizeSpeech 而不碰坏旁边的 STT。

💥

回归风险高

路由与业务同处一处：改 SQL 牵连 HTTP 行为，改 HTTP 又怕碰业务，新增能力人人自危。

🧪

无法单元测试

没有独立文件边界，测试无从挂载，只能靠人工点 UI 验证。

⚔️

合并冲突频繁

大家都在改 index.ts / engines.ts 两个巨型文件，任何一个功能改动都容易撞车。

🔍

故障定位慢

「打开一片黑」需跨壳层 → 服务层 → 渲染层三层排查；只有分层清晰，才能靠 /api/health + headless Chrome 快速归因到打包集成层。

🧗

无法渐进演进

单体文件不支持「只替换一个引擎实现」式的局部演进，任何改动都是全量风险。

1.3 为什么现在改

时机：功能进入稳定期（README 已刷新、打包链路已通）是做结构性收敛的最佳窗口 —— 边加功能边重构会两头风险叠加。
目标：模块化设计、路由与业务分离、数据分层、引擎拆分；每个文件遵守 < 300 行 工程纪律。
约束（关键）：纯重构、零行为变化。安全网不是「小心」，而是三层工具兜底：tsc --noEmit + esbuild 打包 + 全 API 冒烟测试（health / settings / resources / words / notes / chat / coca / dict / tts voices / llm / import）。

优势在哪里

Why It Wins
🎯

单一职责、按域组织

路由层、引擎层、数据层、共享层、前端各归其位；「引擎拆分」让每个 AI 能力独立成文件，互不干扰。

🔗

薄路由 + DI

路由只做「解析 → 调用 → 回包」，业务实现可替换、可单测；ctx 注入让依赖显式可见。

🗃️

数据分层单一入口

连接、迁移、库路径、目录规划收敛在 db.ts，杜绝「两处对同一路径理解不一致」的 bug。

🔌

引擎可插拔

新增 STT/TTS/LLM 供应商 = 新文件 + barrel 注册；本地 ollama ↔ 云端 DeepSeek/Fish 切换只改配置。

🛡️

可验证、零回归

三层安全网（typecheck + esbuild + 全 API 冒烟）让重构大胆做、且能证明「没改坏任何东西」。

🗺️

前后端同域组织

设置分区组件与后端 engines/ 目录一一对应 —— 按同一域组织，导航成本最低。

🚀

进程模型简化

单端口 8787 同时服务 API 与 SPA；dev 的 live-mirror 只开一个地址即得热更新 UI；生产单进程打包体积与故障面最小。

📦

面向打包的设计

dist/ 与 dist-server/ 分离、native 模块 external + electron-rebuild、extraResources 打词典/模型、userData 重定向 —— 架构从第一天就为「能发布」服务。

场景判断：这套架构适合什么

When to Use

1.1 什么时候用这套架构（选这套）

🔒

本地模型 + 隐私优先

需要离线可用、数据不出本机的单机工具。

🟢

核心能力有 Node 库

echogarden / onnxruntime-node / better-sqlite3 / ffmpeg 子进程。

🖥️

桌面分发 + 未来云同步

dmg/安装包分发，且未来可能加多设备同步。

1.2 什么时候别用

场景选型原因
包体积/内存敏感、纯 UI + 少量系统集成Tauri 2（Rust 侧载）包小 10 倍、内存低；但 Node 生态库要么重写要么 FFI，成本高
纯在线工具、无桌面分发需求Web 应用（Vite SPA + 云 API）不需要壳层与本地模型
多用户 / 账号体系 / 服务端协作前后端分离远程部署本地优先的假设不成立
核心模型只有 Python 实现Python 后端（FastAPI 侧服务）Electron 调 Python 子进程也可以，但增加部署复杂度
决策规则：先问「核心 AI/媒体能力有没有成熟的 Node 库」——有 → Electron 方案；没有且必须 Rust 性能 → Tauri + 原生模块；都没有 → 考虑 Web。

7.1 稳定性实践

❤️

健康检查握手

Electron 开窗前轮询 /api/health（超时兜底），server 没起来不闪窗。

🔐

单实例锁 + 优雅退出

requestSingleInstanceLock + second-instance 聚焦已有窗口；窗口全关 kill 服务子进程。

🌐

代理感知网络

Node 内置 fetch 忽略代理环境变量 → EnvHttpProxyAgent 启动时全局注入，无代理直连。

🧭

dist 路径候选探测

esbuild 改变 __dirname 深度 → 候选数组 find(exists(index.html)) 兜底。

🪂

dev 镜像容错

live-mirror 代理 Vite 失败时 fallback 到 dist 静态托管。

🛡️

并发与缓存

multer 限流（500MB）、ffmpeg 子进程、转写/分析结果缓存、STT 去重守卫。

7.2 效率实践

⚡

构建分离

build（Vite 前端）与 build:server（esbuild 后端）独立，互不阻塞、可缓存。

🕒

懒加载大资源

只读 JSON 首载后缓存内存；模型 ensure 只跑一次。

💾

分析缓存

转写/分析按资源缓存（实测 2.4MB 缓存直接命中）。

📏

< 300 行纪律

文件小 → 认知负载低 → 开发/评审/排错都快（最被低估的效率手段）。

8

已知坑（lingutribe 实战踩过，直接避雷）

Pitfalls
1

undici 版本与 Electron Node 版本必须对齐

undici 8.x 需要 Node 22，而 Electron 33 内嵌 Node 20 → 服务端 import 即崩、窗口一片黑。✅ 锁 undici@6.28.0（Node ≥ 18.17）

2

esbuild 打包改变 __dirname 深度

src/server/（到 dist 2 级）vs dist-server/（1 级）→ 静态托管路径找不到 → 黑屏。✅ 候选路径探测 find(exists(index.html))

3

native 模块 ABI 双轨

dev 下 npm rebuild（Node ABI）与打包 electron-rebuild（Electron ABI）互斥。✅ 在打包脚本里做 rebuild，别手动来回切

4

Electron 拒绝 NODE_OPTIONS=--use-system-ca

沙箱注入会导致 Electron 进程启动失败。✅ 测试 Electron 进程用 env -u NODE_OPTIONS

5

spawn 下 ffmpeg 编码器兼容

spawn 调 aac 进 .mp3 会 exit 234。✅ 静音占位一律用 WAV；真实 TTS 返回的 mp3 不受影响

6

Vite 默认只绑 localhost

dev 服务需 --host 0.0.0.0 才能被其它进程/容器访问。

7

沙盒 iframe 无 localStorage

预览环境启动即崩。✅ 提供 shim

8

端口逻辑不一致

曾出现 server 忽略环境变量端口、curl 打错端口导致「假失败」。✅ 端口逻辑统一，测试前先确认监听端口
